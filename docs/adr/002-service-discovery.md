# ADR 002: Service Discovery — Ephemeral Ports, Authority Routing, Wildcard DNS

**Status:** Accepted
**Date:** 2026-08-08
**Relates to:** [001](001-core-architecture.md), [004](004-service-lifecycle.md)

## Context

Developers hit "port already in use" constantly, and maintaining a static map of
which service owns which port is tedious and goes stale.

In production on Fly, this problem does not exist: each Machine has its own 6PN
address, services bind a fixed port, and callers dial
`http://payments.internal:9777`. There is no registry and no registration.

The design goal is therefore not "solve discovery" — Fly already did — but
**make the local dial string identical to the Fly one** while eliminating
collisions on a single shared machine.

## Decision

* Services bind port `0`; the OS assigns a free ephemeral port.
* Services report that actual port to `voya` over the registration stream
  (ADR 004).
* The `voya` proxy binds `127.0.0.1:9777` and routes on the **`:authority` /
  `Host` header**, forwarding to the registered ephemeral port.
* **Name resolution for our own services is a client dialer**, not DNS. The
  `voya` client library installs a `DialContext` that sends any `*.internal`
  host to `127.0.0.1:9777`. The URL — and therefore the `Host` / `:authority`
  header — is untouched, so the proxy still routes by name; only the TCP
  destination changes. When `FLY_APP_NAME` is set the dialer is a no-op and
  ordinary 6PN resolution applies.
* `voya` **also** serves DNS on `127.0.0.1:9778`, answering **every**
  `*.internal` query with `127.0.0.1` — a static wildcard with no per-service
  records and no update path. This exists for consumers that are not our Go
  services: `curl`, `grpcurl`, Postman, browsers.
* That path is wired by a one-time `/etc/resolver/internal` entry on macOS
  (`nameserver 127.0.0.1`, `port 9778`), or the systemd-resolved equivalent on
  Linux, generated by `voya dns install`. It is **opt-in**: no Go service needs
  it.
* Fleet convention: every service declares `9777` in its `fly.toml`.

**Amendment 2026-08-16 (#156):** `voya dns install` writes the macOS entry —
its first line a marker naming voya, then `nameserver 127.0.0.1` and `port
<dns_port>` from the same configuration `voya run` reads — idempotently: an
identical file is left alone, voya's own file for another port is rewritten,
and a file without the marker is refused with its contents shown, because a
developer wrote it. `voya dns uninstall` removes exactly the marked file and
nothing else, refusing an unmarked one the same way; the objection to
`/etc/hosts` management below — stale global state left behind — applies to
a file voya writes unless voya can take it back. Off macOS both commands
decline and exit 2: the "systemd-resolved equivalent on Linux" above names no
mechanism yet, and which one it is stays open as #155.

**Amendment 2026-08-16 (#155):** the Linux mechanism is a **systemd-resolved
drop-in**, `/etc/systemd/resolved.conf.d/voya.conf`: the same marker line,
then `[Resolve]`, `DNS=127.0.0.1:<dns_port>` and `Domains=~internal`. The
tilde makes `internal` a *routing-only* domain — queries under it go to voya
and nothing else changes, where a bare `Domains=internal` would also append
`.internal` as a search suffix and have the host try `anything.internal` for
every unqualified name it looks up. The install rules are macOS's, unchanged:
identical is already installed, voya's own file for another port is rewritten,
an unmarked file is refused with its contents shown. resolved reads its
drop-ins only at startup, so a *changed* file is followed by `systemctl
restart systemd-resolved` — and only a changed one, since a restart is a live
change to how the machine resolves every name.

**A third condition, measured 2026-08-16 and the sharpest of them: resolved's
global scope must not already route every name.** `resolved.conf`'s `DNS=`
and `Domains=` are two independent lists, not a scoped pair — the drop-in
cannot say "send `.internal` to *this* server" the way macOS's
`/etc/resolver/internal` can — and drop-ins accumulate rather than replace
(`man 5 resolved.conf`: "for options which accept a list of values, entries
are collected as they occur in the sorted files"). So voya's server joins the
global list, and a global `Domains=~.` — a pinned-resolver policy, a VPN, a
managed image — sends `.internal` to whichever global server answers first.
An upstream NXDOMAIN for `.internal` is a *successful* answer, so the query
ends there. Measured on a NetworkManager desktop configured that way: install
reported success, `resolvectl query payments.internal` said not found, and
`tcpdump` on voya's DNS port caught **zero packets** across two lookups.
`Preflight` therefore asks resolved for its routing domains and refuses,
naming the catch-all and the mechanisms that can scope (dnsmasq's
`server=/internal/127.0.0.1#<dns_port>`). Only the *global* scope refuses: a
per-link `~.` loses to `~internal` under longest-match routing, so refusing
on one would refuse a host the wiring works on. This is the limit of the
drop-in as a mechanism, recorded here rather than discovered again.

Two host conditions are established before anything is written, because
neither is recoverable afterwards: systemd-resolved must be **active** (a
drop-in for a service that is not running is read by nobody), and it must be
**v246 or newer**, which is where a port in `DNS=` became legal. Measured
2026-08-16 against a real v245 (ubuntu:20.04, `systemd 245.4-4ubuntu3.24`, as
PID 1 in a container) rather than taken from the changelog, since the
threshold decides which hosts voya turns away: resolved does not drop the port
and fall back to `127.0.0.1:53` — it rejects the whole address and configures
no server at all, logging `Failed to add DNS server address '127.0.0.1:9778',
ignoring: Invalid argument`. That is worse than a wrong port, and it is why
this is a refusal rather than a warning. Each failure exits 2 with its own reason, and the two that
mean "this host does not run resolved" carry the way forward: wire `.internal`
to voya's listener with whatever this host does resolve through (`dnsmasq`:
`server=/internal/127.0.0.1#<dns_port>`), or skip DNS and dial through the
voya client, which needs none of it. Per-link `resolvectl dns`/`resolvectl
domain` was the alternative and is rejected: it is bound to an interface, so
it dies with the link, does not survive a reboot and answers nothing for a
laptop that moves between wifi and ethernet — the file is what a one-time
install means.

What the drop-in cannot do is claim `.internal` for itself against a host that
already names a global resolver. `DNS=` accumulates across `resolved.conf` and
every drop-in — an empty assignment is the only reset — and the servers it
names belong to resolved's *global scope*, not to the routing domain beside
them. So on a host whose own `/etc/systemd/resolved.conf` sets, say,
`DNS=1.1.1.1`, the global scope becomes `1.1.1.1 127.0.0.1:<dns_port>`,
resolved asks the first and rotates only on failure or timeout — never on
NXDOMAIN — and `*.internal` comes back empty from upstream. voya does not
write `DNS=` twice to reset the list first: that would take the host's own
resolvers away from every other name, which is exactly the "changes something
else" this ADR refuses. Such a host is the unwirable host again, with the same
way out — send `.internal` to voya's listener through whatever it does resolve
with — and `voya doctor` is what names it: the system path measures
not-answering with the file installed, which is the one row that says the file
is there and something ahead of it is answering.

The second host in that same row is the one where **resolved runs and the
machine's own resolution does not go through it**: a static `/etc/resolv.conf`
naming real upstreams, or `dnsmasq` or `resolvconf` ahead of resolved — the
ordinary state of many servers and containers, and of NetworkManager's
`dns=default`. `Preflight` establishing that resolved is there and can carry
the wiring says nothing about whether anything asks it, and these two questions
come apart. *Amended 2026-08-18 (#186):* **refused**, as the other three
preflight failures are — exit 2, nothing written, with what voya established
and the way forward. Measured first, in a `debian:stable-slim` container with
systemd 257 as PID 1 and the failing shape as its default: `voya dns install`
succeeded, `resolvectl query payments.internal` answered `127.0.0.1` from the
drop-in, and `getent ahosts payments.internal` — getaddrinfo's path, the one
curl and browsers take — answered nothing; pointing `/etc/resolv.conf` at the
stub was the one change that made it resolve. Refusal rather than a warning
because the file voya writes is a claim that `.internal` resolves, and a
warning would leave that claim standing on a success line while the failure it
hides is the silent one — `voya call`, `curl` and the browser simply not
finding the name. Three of four preflight outcomes refusing and the fourth
warning would also leave a developer unable to predict what an install line
means. What it costs, accepted: a host the probe cannot prove but which does
resolve through resolved is turned away and has to wire `.internal` by hand,
or point the system at resolved as the refusal says. That is why the probe is
a **disjunction of the shapes that do work** — `/etc/resolv.conf` a symlink
into `/run/systemd/resolve/` (to `stub-resolv.conf` or to resolved's own
`resolv.conf`, whose contents alone look static), `/etc/resolv.conf` naming
`127.0.0.53` whatever file it is, or `resolve` on `/etc/nsswitch.conf`'s
`hosts:` line — rather than a test for one blessed configuration, and why each
shape has its own row in the test and each half of the disjunction its own
mutation. The one shape it cannot tell from a static file is a *copy* of
resolved's uplink `resolv.conf`; that host is refused, and the refusal's advice
is how to point it at resolved. Not a routing question, so `resolvectl` is not
asked — the two files are read, over the same seam the command questions use,
so every row runs from any OS. `voya doctor` still names the state after the
fact for a file installed by hand or by an older voya: its "installed, but the
system did not resolve through it" row says the restart first and then that a
restart changing nothing means this host may not resolve through resolved at
all.

`voya doctor` and `voya status` gate the file's meaning on **two** questions
from here on, not one: the OS has a wiring this ADR specifies, *and* this
machine is running the thing that reads it. A drop-in on a Linux host with no
systemd-resolved is as inert as an `/etc/resolver` file on Windows, and #96's
ban — never prescribe a file nothing here reads — covers both. The system-path
probe follows the same reasoning onto Linux: `getent ahosts`, which goes
through NSS and therefore measures the path `getaddrinfo` itself takes, rather
than `resolvectl query`, which reaches systemd-resolved over D-Bus and so
answers for a mechanism the system's own resolution might not be using.

`.internal` is an ICANN-reserved private-use TLD, so it cannot collide with
public resolution.

**Amendment 2026-08-18 (#184):** voya answers `.internal` over **UDP and
TCP**, on the one `dns_port`, loopback only — the same address, the same
answers, one answering function behind both. RFC 7766 makes TCP a SHOULD for
a DNS server, and the clients that need it are the debugging ones: `dig +tcp`,
a local resolver forwarding a TCP client (dnsmasq forks a TCP forwarder for
one; systemd-resolved's stub accepts TCP on 127.0.0.53), and any client
retrying a UDP answer that came back truncated. Before this each of them met a
bare connection refused, surfaced as SERVFAIL with no sentence attached, which
is the failure ADR 005 exists to remove. The truncation flag now means what
it says — a name too long for a 512-byte datagram is answered whole on the
retry — though no name voya can route comes near that limit. Both sockets or
neither: a port free on UDP and held on TCP is a startup failure naming the
port, not a voya answering on one transport and dead on the other.

## Alternatives considered

**1. SRV records carrying host *and* port.** The instinctive choice — it is the
Consul pattern, and it would carry the ephemeral port for free. Rejected on a
hard technical constraint: **`net/http` does not resolve SRV records**, and
`connect-go` is built on `net/http`. `grpc-go` only ever consulted SRV for the
deprecated grpclb lookup, never for ordinary endpoints. Making SRV work would
require installing a custom resolver in every client — reintroducing precisely
the dev/prod code divergence this design exists to eliminate.

**2. Dynamic per-service DNS records, updated on registration.** Rejected as
unnecessary. Since every name resolves to loopback, the answer is constant; a
wildcard has no update path to get wrong and no second source of truth to drift.
It also produces better diagnostics: an unknown name reaches the proxy, which
can answer "service `paymnets` not registered — known services: payments,
billing, …" rather than an opaque NXDOMAIN.

**3. `/etc/hosts` management.** Rejected: no wildcard support, requires root on
every change, and leaves stale global state behind when `voya` exits badly.

**3a. DNS as the *only* resolution path.** *(the original form of this ADR)*
Rejected on 2026-08-08. It made a privileged, per-platform system change a hard
prerequisite for running anything, and forced every service to be built
cgo-enabled locally or silently fail to resolve. The dialer removes both for the
traffic that matters, and DNS survives as opt-in support for tools. Since the
fleet is Go-only, the dialer's one limitation costs nothing.

**4. Path-based routing through a single front door.** *(the original draft)*
Clients would dial `localhost:9777` and route on the gRPC method path. Rejected:
that dial string looks nothing like Fly's, so client code diverges; and REST
paths across services (`/healthz`, `/v1/users`) collide silently under
first-match-wins routing.

**5. A checked-in file assigning fixed ports per service.** Rejected: that is the
tracked-port-numbers problem we are removing.

## Consequences

* **Positive:** Port collisions eliminated, and dial strings are identical in
  dev and prod.
* **Positive:** Nothing to keep in sync. DNS is a constant; the registry lives
  in one process.
* **Positive:** Authority-based routing disambiguates requests that share a URL
  path across services — including gRPC server reflection (see ADR 003).
* **Positive:** Services need no privileges, no system configuration, and no DNS
  server running. The dialer works on first run, on any OS, with nothing to
  install.
* **Positive:** The dialer is immune to the resolver trap below, because it never
  consults the system resolver at all.
* **Negative:** The dialer only helps Go code. Accepted: the fleet is Go-only by
  decision (ADR 001), so it covers all service-to-service traffic.
* **Negative:** It is a required import in every service. In practice this is
  free — ADR 004 already requires the registration hook in `main.go`, and both
  live behind the same call.
* **Negative:** Human-facing tools — `curl`, `grpcurl`, Postman, browsers — still
  need the DNS path and its `/etc/resolver` entry, which needs sudo (`sudo
  voya dns install`). Nominally
  opt-in, but in practice most developers will want it, since Postman-driven REST
  validation (ADR 003) and browser gRPC-Web both depend on it.
* **Negative — sharp edge, now scoped to the DNS path only:** on macOS,
  `/etc/resolver/*` is honored by `getaddrinfo`, which Go reaches through **cgo**.
  A binary built with `CGO_ENABLED=0` (or running under `GODEBUG=netdns=go`)
  falls back to Go's pure resolver, which reads only `/etc/resolv.conf` and
  **ignores `/etc/resolver` entirely**. The failure is confusing — `dig` and the
  browser resolve fine while a Go program gets NXDOMAIN. Before the dialer this
  gated the whole system and forced cgo-enabled local builds; it now affects only
  Go code that deliberately bypasses the dialer, and `voya doctor` must still
  detect it (**pin in a test** — issue #6). *Amended 2026-08-13 (#6):* "falls
  back to Go's pure resolver" is a property of the toolchain, not of the flag —
  since Go 1.20 a darwin build without cgo still takes the system path through
  a direct libc call, and whether that call honours `/etc/resolver` is nothing
  a build flag can tell you. Only `-tags netgo` and `GODEBUG=netdns=go` are
  deterministically on the pure resolver. `internal/doctor` therefore measures
  each path at runtime instead of deriving them from the build, and its tests
  pin whichever of this issue's three rows the host can prove. Its reports name
  only what it measured: the system path through `dscacheutil`, which is the
  one `getaddrinfo` — and so curl and browsers — takes. `dig` sends its own
  queries to `/etc/resolv.conf`'s nameservers rather than going through that
  path, so doctor does not probe it and does not speak for it; "`dig` resolves
  fine" above is the symptom as first reported, not something measured here.
* **Negative:** Registration is unauthenticated and trust-on-first-use — any
  local process can claim a service name. Accepted for a dev tool, and bounded
  by binding all three listeners to `127.0.0.1` explicitly, never `0.0.0.0`.

## Duplicate registration

**Resolved 2026-08-08: evict-and-replace, loudly.** When a service registers a
name that is already held, `voya` closes the incumbent's stream, replaces the
registration, and emits a prominent warning naming both the evicted and the
incoming instance. **One exception since 2026-11-02 (#339): a registration
matching the holder's pid and port joins it instead.** See the amendment at the
end of this ADR.

This follows the common case. A name re-registers because the developer just
restarted that service, so last-writer-wins matches intent nearly every time.
The cost falls on the rarer workflow — running `main` and a feature branch side
by side — where the first instance is silently deposed. The warning exists for
exactly that case, and it must read as an event rather than a log line: the
failure it prevents is spending twenty minutes debugging a build that stopped
receiving traffic.

Rejected: **rejecting the second registration**, which is safer for side-by-side
work but makes the overwhelmingly common restart fail until the stale entry
clears; and **instance-labelled routing**, which is real complexity — a routing
key beyond the authority, plus a way to select it — for a case rare enough not to
earn it yet. If side-by-side comparison becomes routine, that is the design to
revisit.

Whatever happens, silent round-robin between two builds remains unacceptable.
`voya status` surfaces evictions after the fact (ADR 005), so the condition is
recoverable even if the warning scrolled past.

**Amended 2026-08-11 (#43): the announcement sits at `LOG_LEVEL_WARN`, so
`log_level = LOG_LEVEL_ERROR` silences it.** "Loudly" above is unconditional
and, since `log_level` began deciding what voya prints, no longer is. The
config schema documents `LOG_LEVEL_WARN` as "failures plus the events ADR 002
requires be impossible to miss", which is where both this warning and the
reclaim below were put; an `ERROR` that still printed them would be a synonym
for `WARN`, and "verbosity floor" would stop being true of the one level most
likely to be set for quiet. So the obligation holds at the default and at
every level above `ERROR`, and a developer who asks for failures only has
asked for this too. `voya status` remains the after-the-fact record at every
level — which is what keeps the condition recoverable rather than lost.

### What the deposed instance does next

**Resolved 2026-08-10 (#27): it keeps running, and asks for the name back for
a bounded while without ever taking it.**

Leaving the question open stopped being viable once the client existed. A
deposed instance that reconnects the ordinary way re-registers, deposes
whoever deposed it, and the two swap the name for as long as both run. The
obvious fix — never reconnect after an eviction — is safe and throws away the
workflow that makes local development bearable: replace a service to try a
fix, find the replacement worse, kill it, and have the original resume serving
with its state and its debugger session intact.

So the retry exists, and two properties keep it from being the same bug at a
slower period:

* **Every attempt is conditional.** `RegisterRequest.only_if_unclaimed` tells
  voya to refuse rather than evict, so a claim against a live holder always
  loses. Ordinary registration stays last-writer-wins — a service restarting
  has to take its name back from the copy that has not finished dying — and
  those are opposite needs that happen to share a message.
* **It is bounded.** Five minutes by default, then it gives up. Long enough
  for "I killed it, give me the old one back", and expired long before anybody
  walks away from their desk, so a process forgotten at the end of the day
  cannot take a name back the next morning.

The reclaim is announced as prominently as the eviction was. That is not
decoration: traffic has returned to a build somebody replaced *because it was
wrong*, which is this section's twenty minutes of confusion arrived at from
the other side.

Rejected: **exiting non-zero when deposed**, which is the most honest signal
and also destroys the debugging session that is usually the reason the
developer is sitting there.

## Amendment 2026-10-31 (issue #314): the DNS check is `voya dns check`

Where this ADR says `voya doctor` or `internal/doctor`, the check is now `voya
dns check` and `internal/dnscheck` (ADR 005's amendment of this date says why).
What it measures, and every row of it, is unchanged. Its report has no
aggregate over other checks now, so the verdict is the DNS check's own.

## Amendment 2026-11-02 (issue #339): a matching registration joins the holder

The rule above has one exception. A registration whose pid is non-zero and whose
pid and port match the holder's is treated as that instance reconnecting. It
joins the existing entry: nothing is closed, nothing is evicted, nothing is
announced, and traffic stays where it was. Any other registration of a held name
is an eviction as before, including one quoting the holder's pid on a different
port, and including any registration with a pid of zero.

`RegisterRequest.pid` therefore decides something now. Until #308 it only named
instances in a warning. It is a number the client states and voya cannot check,
so a match proves nothing about who is asking. Joining is accepted anyway
because it moves no traffic at the moment it happens.

ADR 004's amendment of this date gives the matching rule for when the name goes.
The costs are stated there, because they come from that rule. `SECURITY.md`
states them for a reader of the security policy.
